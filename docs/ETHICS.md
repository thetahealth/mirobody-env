# Ethics, data provenance and limits of use

> Written for **external readers**. Read this before you read any number in this repository.

## In one sentence

**Every patient in this benchmark is generated. No line of it describes a real person.**
De-identified real EMR entered in **one way**: as aggregate statistics (medians,
abnormal rates, spreads, one correlation, one dirty-data rate) that set the
distributions the generator samples from. No record, and no value of any single
patient, was copied into a case.

---

## 1. The data is synthetic

The task specifications in `inputs/**`, the patients in `results/**/cases.jsonl`, and
every lab value and wearable reading on a question are **generated by `haenv/build.py`**
-- either by formula, or rendered by code after an LLM picks a baseline.

Every artefact carries the marking `SYNTHETIC, evaluation only, not medical advice`.

**Do not** use this data, or a model evaluated on it, for any clinical decision. The
benchmark measures model behaviour in a **controlled synthetic setting**, not clinical
safety.

---

## 2. Exactly where real EMR entered

| Question | Fact |
|---|---|
| Was real data used? | **Yes.** De-identified EMR, via `tools/calibrate_from_real_emr.py` and a companion correlation tool; neither tool ships |
| Used for what? | Setting distributions that would otherwise be estimates: per-cohort baseline medians, abnormal rates and between-patient spreads for a few labs, one between-patient correlation, and the rate at which a recorded weight repeats the previous one |
| Did it reach the questions? | **Yes, as distributions.** The calibrated values sit in `registry/` and the generator samples every case from them. The tools themselves only print tables; a person copied the numbers into the registry, each entry marked with its provenance |
| Were patients copied? | **No.** Only aggregate statistics were extracted, never a record or a single patient's value |
| Where are the per-reading derivatives? | Kept outside this repository; **not in the copy you have** |

### This leaves a known reproducibility gap

The calibration derivatives are not in the repository, so the calibrated values
**cannot be re-derived here by an external reader**. This is a deliberate trade between
privacy and reproducibility.

### Three blind spots the calibration tool reports about itself

* **Different population.** The real data comes from inpatients and outpatients with
  diabetes, hypothyroidism and coronary artery disease. This benchmark is set among
  **people losing weight at home on GLP-1 or metformin**. The baselines are a reference,
  **not a substitute**.
* **Only the labs line up.** The 12 wearable indicators (steps / HRV / sleep / stress /
  SpO2) have **no counterpart at all** in the real EMR, so this corpus cannot calibrate
  them. The wearable streams are set from a public wearable dataset instead; which
  streams have an empirical anchor and which do not is listed in
  [`DATA_CARD.md`](DATA_CARD.md).
* **Units were not checked item by item.** Results are grouped by the `UNITS` column, and
  groups with inconsistent units are not merged.

### What was set from real data

Every calibrated entry carries a structured marker, so the list below is a query, not a
recollection (`review: calibrated_on_real_emr` or a `calibration:` field in `registry/`):

| Where | What was set from the real corpus |
|---|---|
| `registry/indicators.yaml` | cohort distributions for `HbA1c` and `fasting_glucose` (type 2 diabetes), `LDL` and `triglycerides` (dyslipidemia), `AST` (MASLD): median, abnormal rate, between-patient spread; and the between-patient correlation of `HbA1c` with `fasting_glucose` (r = 0.7133, 670 patients) |
| `registry/clinical_baselines.yaml` | the diabetic-cohort `HbA1c` baseline |
| `registry/artifact_rates.yaml` | the carried-forward rate of recorded weight (0.1431, a nurse copying the previous reading), applied after the kernel by `haenv/post_inject.py` |

These entries are live: the generator reads the registry on every build, so packs built
from the current code (including `ddx-timeline` and `ddx-workup`) are sampled from them.

Everything else keeps its prior provenance: literature values, `haenv-authored` estimates
marked `review: pending`, or, for the wearable streams, a public wearable dataset (see
[`DATA_CARD.md`](DATA_CARD.md)).

## 3. Where the medical content comes from, and how far it has been reviewed

* Reference ranges and test names come from an upstream indicator table
  (`upstream:indicators/indicator_list_comprehensive.csv`), each tagged with its `source`.
* Entries written here are tagged `haenv-authored` and carry `review: pending`. The
  **pending state travels all the way into the report**; it does not disappear on the way.

  For the physiological event kernels: **69 kernels, 95 kernel-by-stream entries**,
  `source` is `haenv-authored` for all of them, `review` is `pending` for all of them, and
  none carry a citation. The direction (which way an event pushes a stream) has clinical
  consensus; **the magnitude and time constant are engineering estimates** with no
  citable literature value. Attaching a fake citation would be worse than marking them
  pending, so they stay pending. Separately, 23 of the 35 registry tables have no
  `source:` field at all.

* **Six rare-disease families (`HD-UNI-*`) are in the production queue carrying
  `clinical_review: pending`.** This is an explicit trade of **confidence in clinical
  content** for **world richness**.
* The relations (Friedewald, Payne-corrected calcium, De Ritis and others) each had their
  source verified against the literature, and were **rewritten into this repository's
  registered units before entering the code** rather than copied in the paper's mg/dL
  form: Friedewald's LDL term is `TG/5` in mg/dL but `TG/2.2` in mmol/L, and the commonly
  cited albumin-corrected calcium coefficient of 0.8 is a mmol/L adaptation of Payne's
  original 1.0.

**The medical content in this repository has not had an overall review by a licensed
physician.** It is sufficient to support judgements of the form "is the model's answer to
this question right", and **not** sufficient to support any conclusion about real clinical
practice.

## 4. How evaluated models are handled

* Evaluation calls third-party model APIs. **Prompts and questions are entirely synthetic**
  and contain no real patient information.
* Raw model responses are stored in `results/**/responses.jsonl` so that a change to the
  judges can be answered by a **recompute** (the rule is: persist raw output, not just
  scores). Those responses are model-generated text and contain no real-person data.
* API keys are injected from `config.yaml:env_file`; they **are not logged and do not
  enter any artefact**.

## 5. Three things that get misread

1. **A leaderboard score is not clinical ability.** The overall score is a weighted mean of
   construct metrics multiplied by (1 - hard-gate failure rate). It measures performance on
   this benchmark's question types; extrapolating to the clinic needs independent evidence.
2. **A leaderboard holds only under one judge version.** Change the scoring code and every
   leaderboard on disk is invalidated at once (the publication gate `assert_publishable`
   refuses). A cited number must carry its `judging_sha16` and freeze revision.
3. **None of the four entries in `trace_unimplemented` means "not implemented".**
   Per-cell artefacts carry a `trace_unimplemented_status` column
   (`TRACK_GAPS` in `haenv/process.py`). The four are
   **`form_partial` x3 + `judge_unexercised` x1**, and
   **`no_production_judge` (the judge does not exist) accounts for none**:

   | Track | Status | What is the case |
   |---|---|---|
   | `discriminative_tool` | `form_partial` | The non-interactive form **has real-model readings**; the interactive form has none |
   | `revision_grounded` | `form_partial` | The slice form has readings; the multi-turn form has **no readings from a non-stub solver** |
   | `neutral_window_drift` | `form_partial` | The slice form has readings; the multi-turn form **is implemented but has produced no non-empty value** |
   | `gap_naming_precision` | `judge_unexercised` | The judge exists; no `gap_*` key appears in any batch |

   **Do not read their empty values as a score of 0**, and do not read them as "this track
   does not exist".
